# 客户之声 —— 作者作为插件的真实用户

> 本文件是 v2.0.0 验证轮（PBI-7 前置）中「客户之声」摊位的记录：作者 SeaPawn 作为 IDEO-Scrum 插件的创作者兼真实用户，写下自己使用这套方法论的流程与感悟。专家会议的技术证据（1.x 复盘、插件解剖）由助手整理；**这里的每一句体验与判断来自作者本人**，助手补记的分工与研判已单独标注。

## 我的使用流程

### 一般使用流程

（作者口述落盘 2026-08-30。）

#### 〇、项目骨架

拿到项目，先建项目骨架——用 repo-init 即可，简单，不赘述。

#### 一、IDEO 文件夹：研究工作正式开启

建一个叫 **IDEO** 的文件夹——关键动作，它代表**研究工作正式开启**。

此刻的状态：**问题有名字、没定义**。知道这个项目要解决一个什么问题（一句话能说），但关于问题的细节全是问号：是不是真问题、在谁身上发生、有多痛、怎么解——完全不知道。脑里往往还揣着半个答案：这是个危险信号，答案若是假的，后面所有工作都是把方向带偏。

**一条重要原则：先定 goal 和挑战，再做深度研究。** 深研究其实可以提前很多很多（先做完全没问题），但为了研究收敛住，还是先定后研——承诺在前，研究在后；没有 goal 的研究是黑洞。

#### 二、design 文件：定研究内容

IDEO 文件夹里，第一件事是开一个**设计冲刺**：先建 **design 文件**，分四部分。先把第一部分定死：

- 挑战宣言
- 设计目标
- 冲刺问题

三个都很重要。**定死之后才能往下走。**

**反馈环**：背景研究若否定了冲刺问题——回头修改第一部分，再走；不是一次写完就完。

#### 三、背景研究（empathize）

主要是 empathize 方法论：说明整个问题的背景是什么、然后怎么去做。形式按需（背景调研 / 访谈 / 专家会议）——solo 情形下「专家」就是作者自己：口述，助手记录，讲不清才追问（本次验证轮的客户之声即这一产出）。

这一步有**两个产出**：

1. **背景调研文档**——一般量不小，可专门落一个文件夹，也可直接放 docs/ 里；
2. **Map**——**必须有**，有专门方法论支撑，写进 design 文件的 Map 部分。

#### 四、选 target：对着 map 选，按 PO 的决定顺序

Target 阶段是**四阶段法**：

1. **定 target goal**
2. **选择问题进来** —— 1+2 形成 target 的第一部分的两个小节；
3. **定 map** —— 把 design 文件里的 map 选择进来（抄录，只抄不细化，map 仍是第二节）；
4. **对 map 细化** —— ⚠️ 时机待定：plan 时做 / target 冲刺时做（倾向此）/ 冲刺中的小任务。*「这个精化，真的很难把握。」*

#### 五、同源发现：target 文件 ≈ SprintBacklog

（先看 Scrum 侧——这里就有可借鉴的精华。）

进入 sprint，第一步是写 SprintBacklog.md：

1. 明确 sprint goal
2. 抄录 DoD 相关内容（摘抄即可）
3. 抄录 PBI（直接抄录，**PBI 就类似 map**）

然后做精化，分两部分：① 定义验收标准与 test；② 细化 PBI 供 LLM 更好理解。Scrum 两个角色可以对抗（待点名）；IDEO 侧估计放一个角色，目的就是**快**。

> 关于 ②「细化 PBI」——判断：**没必要**。这完全是第三部分「如何做」的活——就是拆解 PBI 嘛。

回到 target：map 抄录足够了、不需要细化，那 map 仍是第二节，然后**直接分叉进方案节**——方案节本质就是细化 map 的场所，和 Scrum 第三部分「如何做」相通。但 map 抄录时**有一件事必须做：定验收标准**（和 test 同工），然后再开始找方案。

**同源结构表**（助手整理）：

| target 文件 | SprintBacklog | 人参与？ |
|---|---|---|
| target goal | sprint goal | 人 |
| 问题（选择进来） | DoD 摘抄 + PBI 抄录 | 人 |
| map（抄录，不细化） | PBI ≈ map（抄录，不细化） | 人只抄不造 |
| 定验收标准 / test | 验收标准 + test 定义 | **人全力参与** |
| 方案节（= 细化 map） | 第三部分 如何做（= 拆解 PBI） | AI / developer，人不管 |
| 结尾：人验收 | 结尾：人验收 | 人 |

**分工原则**：验收标准（AC）就是 What 与 How 的边界线——人在第一部分必须懂这么几点：goal、question、DoD、map、PBI、test/验收标准（这些是人的主场）；AI 干 How，人不管。落到执行：人主要参与「与 master/SM 一起定义开局计划」与「结束验收」，中间怎么做不参与。

**（助手补记，待作者确认）**：「细化 PBI 供 LLM 理解」疑为伪需求——LLM 读原文当场理解，不需要预处理；它需要的是「不懂就追问」，细化的正确场合是「如何做」阶段的第一轮对话，不是计划文档。计划文档需要的是「装箱」（跨文档引用喂全），不是「打磨」。

#### 六、未决清单（维持开放）

- **map 精化的时机**——作者原话：「我有点拿不准」/「这个精化，真的很难把握」/「还是蛮难做的其实」
- **Scrum 两个可对抗的角色**：具体是谁对谁（PO/SM 定验收标准+test 对 developer 执行？还是 master 教学对 designer-developers 执行？）——待点名
- **IDEO 侧单角色**：是谁（master？designer？）——待确认
- **target 的落位**：独立文件（TargetMapping）还是 design 文件第三部分——待确认
- **「选择问题进来」的问题来源**：design 文件第一部分冲刺问题中命中此 target 者，还是背景文档中挑新问题——待确认
- **solo 边界无裁判**（助手研判，待作者验证）：solo 模式下 PO/developer/验收入都是自己，对抗角色不存在，边界变成自己答应自己的事。「精化难把握」可能就是没人守边界。master 的本职或许不是教学，而是**当那个对面的人**。
